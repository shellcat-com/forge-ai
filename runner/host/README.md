# Dedicated Linux host lifecycle: implementation, not deployed isolation

This directory implements the durable host inventory, lifecycle and watchdog logic behind the existing broker. **No real LinuxExecutor is supplied, no service is installed, and no privileged operation is run by these imports or tests.** `UnavailableFirecrackerDriver` remains the production default. Do not connect this controller to a host/container app executor.

`HostInventory.acquire(directory)` obtains a lifetime singleton lock and serializes fsynced inventory transactions. It retains operation/environment/database identities and permanent tombstones, including destroy-before-create. A second owner is refused. Never remove a stale owner.lock until the previous process is fenced. A process with any unsettled launch or cleanup invocation cannot release ownership. The journal has a16MiB bound; tombstones must not be deleted to reclaim capacity. Any future inventory compaction must preserve them.

`HostLeaseSupervisor.create/renew/destroy` consume the E0 descriptor already authenticated/authorized by SandboxBroker. Adapter wiring uses these lifecycle calls for the existing HostDriver create/renew/destroy methods; guest runCheck/collect still require the absent trusted guest transport. There is no second tenant/job control service or network API here.

Create persists reservation and launch intent first. Repeated creation does not start another guest. Renew persists the deadline/epoch without depending on control-plane liveness for enforcement. The supervisor never clears a tombstone or permits identity reuse. `watchHost` schedules host-local lease checks each second, independently of worker/control connectivity. Active-time exhaustion and a backwards clock also fence guests; last observed wall time is durable across supervisor restart.

Destroy checkpoints the tombstone before ingress revocation, launcher/VM stop and disposable storage/credential wipe. Each OS call is capped at5s; ambiguous calls are retained and not duplicated while still unsettled. All OS awaits occur outside the inventory transaction. Cleanup passes coalesce per operation. Capacity remains reserved until fresh, operation/attempt-bound OS observations confirm ingress, launcher, VM, volume and credentials are absent. A pass that began with an unsettled launch cannot release capacity even if that launch settles while an earlier absence response is in flight. A fresh cleanup pass is required. Recovery of an uncertain launch similarly requires a confirming pass followed by fresh cleanup.

The LinuxExecutor adapter must provide real kernel/service/storage observations; booleans returned by guests or operator "safe" switches are never evidence. Late/ignored-abort launch success is quarantined and killed on subsequent cleanup. The actual helper must additionally enforce atomic pre-spawn fencing under its per-attempt launcher ownership. That OS integration is not implemented or proven here.

Read-only `preflightLinuxHost` rejects non-Linux before touching host resources. It checks accessible character-device `/dev/kvm`, required cgroupv2 controllers, strictly disabled unprivileged BPF, root-owned non-writable pinned assets and parent directories, symlink aliases and SHA256 drift. Hashing streams bytes through a no-follow file descriptor. Small kernel metadata is capped at4096bytes. Supply real operator-selected firecracker, matching jailer, kernel, rootfs, dependency cache, seccomp filter and supervisor paths/hashes under `/opt/forge/`; there are no fake example hashes or enablement booleans. Even successful preflight reports `executionEnabled:false`: it measures prerequisites, not live isolation or an installed executor.

The systemd, nftables and cgroup files are **uninstalled review candidates**. The service depends on absent operator configuration and a pinned supervisor executable. Its necessary root/capability access requires dedicated-host security review. All launcher/VM cgroups must remain within the service subtree so systemd KillMode covers them if the supervisor exits. Verify the selected kernel/systemd controller delegation and no-internal-process rules before launch. Host pids.max limits VMM threads, not the guest process table; the512-process app limit still needs trusted guest-side enforcement.

Apply the nftables policy only inside an assigned guest network namespace, never the operator's root namespace. It denies IPv4/IPv6/DNS/metadata/lateral traffic and enables no preview ingress. D6 must define the gateway path separately. Guest PostgreSQL loopback is inside the guest, not an allowed host egress exception.

The [Firecracker jailer documentation](https://github.com/firecracker-microvm/firecracker/blob/main/docs/jailer.md) specifies matched static Firecracker/jailer releases and explicit namespace/cgroup settings; [production host guidance](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md) remains part of the actual D2 deployment review. These candidate files have not been accepted by systemd/nft or exercised against Linux. No host hardening claim follows from their existence.

Tests: `npx vitest run tests/engine/e3-host.test.ts`. All20 tests use explicit OS fakes and synthetic descriptors. Evidence covers partition/expiry, late create/destroy races, persistent fencing, singleton lifetime, repeated cleanup, quota retention, observation freshness, clock regression and preflight rejection. It does not pass RFC A09/A10/A13 isolation acceptance. Actual syscall/Firecracker/guest-agent, image build, kernel/resource abuse, network policy, cleanup inventory and privileged deployment tests remain blocked by D2/D7.
