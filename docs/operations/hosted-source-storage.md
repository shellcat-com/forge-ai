# Encrypted source storage on Neon Free

Engine migration 0006 publishes the reviewed PostgreSQL immutable-object implementation and adds a hard installation capacity: at most 64 MiB of retained ciphertext and 10,000 permanent object identities. Existing BYOK/auth migrations remain unchanged. No worker, public object URL or source-adoption API is enabled by the migration.

The existing AES-256-GCM backend binds workspace, project, job, object ID, version and encryption key ID as authenticated data. Separate reader/writer/maintenance logins cannot access control/auth authority or change the capacity policy. User access still requires fresh account and object ownership authorization through the control API; raw object keys and database credentials are internal capabilities, not user authentication.

Writes reserve byte and identity capacity atomically in the same transaction as immutable insertion. Competing writes cannot overrun the cap, and failed inserts roll back their reservation. Orphaned and retired ciphertext remain charged until eligible purge. Purge releases bytes but retains/counts the permanent identity tombstone. The object-count ceiling therefore needs an explicit future migration/archival decision if exhausted; purging alone does not reset it. This bounds metadata as well as source bytes.

Missing capacity policy and exhausted capacity produce `OBJECT_CAPACITY_UNAVAILABLE`; existing readable source remains preserved. The future job controller must persist this as an actionable pause. Neither cleanup nor a quota error may buy storage or raise limits automatically. This cap reserves only Forge's object allowance; the installation must separately account for PostgreSQL overhead, auth/jobs/history and application database usage against Neon's actual remaining allowance.

The hosted installer applies hash-checked migration 0006, explicit CONNECT grants and `docs/examples/hosted-object-version-receipt.sql`. The additive receipt registers the object migration in the control schema ledger after checking its required objects; the original applied SQL remains unchanged. It selects a one-hour orphan grace, one-day deleted-project grace and one-day retired-data recovery window on first installation, preserving existing policies on replay. Source history with authoritative references is never retired merely because a preview expires. Deletion additionally requires project deletion age and every job finished. These are bounded local retention promises, not a backup service or proof of disaster recovery.

Fresh installations create all seven separate runtime logins. For this already-installed four-login control database, use `FORGE_INSTALL_ONLY_OBJECT_LOGINS=true` with a new exclusive mode-0600 `.private` secret output. This creates only the three object logins and leaves existing runtime credentials untouched. `FORGE_INSTALL_SCHEMA_ONLY=true` verifies/applies schema without creating or replacing logins. Never combine these modes.

Configure distinct server-only versioned object encryption keys, separate from auth/session and model-credential encryption. Keep old key IDs available as long as any source or retained backup needs them. Losing the keys loses access to encrypted source. No object encryption key is committed, generated for a browser, or returned in an API response.

Rollback: disable the future source writer/admission first, preserve the schema/keys/source and retire credentials explicitly if needed. Do not drop the database, remove tombstones or rewrite existing immutable versions. Actual hosted source adoption, key recovery and worker/API integration remain release gates until separately demonstrated.
