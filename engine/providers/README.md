# Provider and credential boundary

Task 04 supplies server-only modules; Task 01 owns their live E1 composition. Nothing here adds a route, enables a worker, applies SQL, selects a paid budget, or changes the existing Next.js application provider registry. The required generated stack remains Next.js + strict TypeScript + PostgreSQL.

## Supported transport

`ProviderRegistry` accepts exact administrator-installed `ProviderPolicy` entries. The implemented protocol is `chat-completions-json-v1`: one nonstreaming JSON object, no tools/images/audio/reasoning protocols, no retries/fallback. `openai` is restricted to `https://api.openai.com/v1/chat/completions` and `gpt-4.1-2025-04-14`. There is no default policy or price. Other protocols fail schema validation. A custom provider requires an exact installed endpoint/model policy and its own evidence; an OpenAI-shaped endpoint is not universal compatibility. `status()` exposes policy evidence classification, always with `liveEnabled:false`; actual availability belongs to integrated E1 admission and acceptance gates.

The first adapter has a synthetic end-to-end source-path test, **not live verification**. The official [GPT-4.1 model page](https://developers.openai.com/api/docs/models/gpt-4.1), checked 2026-09-10 UTC, lists this snapshot, 1,047,576 context tokens, 32,768 output tokens, and standard uncached prices $2/$8 per million input/output tokens. These are compatibility inputs, not account entitlement, a frozen price authorization or a benchmark. The [Chat API reference](https://developers.openai.com/api/reference/resources/chat) is the protocol reference. The adapter sends `max_completion_tokens`, JSON object mode, `service_tier:default`, and `store:false` for configured policies; it checks the returned model. JSON mode does not guarantee schema correctness: Zod and semantic source validation remain mandatory.

Every connection validates the exact canonical HTTPS URL and **all** DNS results. IP literals, nonstandard ports, queries, fragments, userinfo, noncanonical spellings and unsupported paths are denied. Only globally routable IP ranges are accepted, with conservative exclusions for IPv4 private/metadata/reserved ranges and IPv6 local/mapped/transition/documentation ranges. One validated IP is pinned into a new Node TLS socket, preserving original Host/SNI and certificate verification. No redirect, proxy environment, second DNS resolution, alternate address retry or pooled socket can replace that destination. DNS is revalidated for the next call. DNS/socket tests are mocked contracts; a deployed egress test remains required.

## Credential connections

`CredentialConnections` takes a server-origin configuration, `CredentialAuthorizer`, `CredentialRepository`, cipher and registry. Mutations read their body lazily after exact origin/authenticated-TLS/owner checks. Input fields are limited to `connect {provider,key}`, `rotate {id,expectedRevision,key}` and `delete {id,expectedRevision}`. The route must enforce a 16 KiB body limit, disable body capture/logging/telemetry and return only the redacted service result. Status is owner scoped and never returns ciphertext, reference paths, suffixes or a raw key. Presence stays `unverified`; there is no paid credential probe.

`transport:'authenticated-tls'` is a **trusted listener/proxy assertion**, never a JSON or forwarded-header field. The route must reject plaintext HTTP and derive TLS from a reviewed ingress configuration. Task 05's strict identity request receives only sessionToken/workspaceId/csrfToken/origin/operation, stripping the transport field. `PostgresCredentialRepository` uses its generic `withAuthorization(request, action(tx,principal))` so owner/session/CSRF/freshness and revocation locks cover the actual read/CAS transaction. An `authorize()` result alone is insufficient for a later write. No UI or HTTP route is mounted by Task 04; Tasks 01/05/08 own that protected user flow integration.

AES-256-GCM uses a fresh 96-bit nonce and authenticated domain + workspace + credential ID + revision + provider + exact destination. `EncryptionKeys.currentKeyId()` selects the write key, while `resolve(keyId)` returns a 32-byte server/KMS-managed key for retained versions. Key buffers are copied before wiping; JavaScript string copies cannot be reliably zeroized. Unknown key IDs or tampered bindings fail with fixed errors. Retain old wrapping key versions only for the approved migration/backup retention window; removing one before re-encryption makes its rows unreadable. The object-store key domain from Task 06 is separate.

Credential rotation increments revision and re-encrypts with the current wrapping key. Deletion creates a tombstone with no ciphertext. Concurrent writes compare revision; the old destination/tenant/provider cannot change. `hostedCredentialResolver` freshly checks worker authorization and current revision before and after decryption. Task 01's dispatch transaction must lock the same credential row and check revision before marking a call dispatched, serializing with rotation/deletion. Already dispatched remote calls may continue or charge after cancellation/deletion. Deleting the Forge connection does not revoke the provider account's key or physically erase retained backups; provider revocation and backup retention remain explicit operations.

Self-hosted `serverCredentialResolver` accepts administrator-owned environment/secret references bound to an exact provider/destination. Request bodies cannot choose environment names or secret paths. `NEXT_PUBLIC_`, `VITE_` and `PUBLIC_` references are refused. Resolve only on the server; never import these modules into client code or generated apps. A reference's presence is not spending authorization.

## E1 accounting and source composition

`accountedProviderHooks` implements the existing `ProviderAttemptHooks`. Its `CallAccounting.reserve(terms)` durably suballocates the job's pre-admitted workspace/global envelope; `dispatch(receipt)` performs a fresh gate and one-winner CAS. Duplicate intent never grants another dispatch. Immutable terms bind tenant/project/job/step/epoch, request hash/UUID, exact provider/model/destination, credential revision, policy digest, full dated price snapshot/digest, token bounds, repair number, stage and deadline. Maximum calls remain 12, repairs 2. Use a new explicit authorized job to change provider/policy/key revision; no automatic paid fallback.

Input bounds include UTF-8 content bytes, per-message framing, request overhead and the schema already present in the context. This conservative **candidate** bound applies only to the configured byte-fallback text tokenizer policy. Its adequacy still requires live/account-specific acceptance; configuration is not proof. Input plus output must fit the model context window. Integer arithmetic rounds each input/output price component upward to microdollars, as specified in engine-decisions.md. Admission blocks missing, expired or inconsistent price snapshots; dispatch must recheck the same job policy after delays.

`PostgresCallAccounting` uses the existing E1 `provider_attempts`, `usage_reservations`, `workspace_quotas` and append-only `usage_ledger`; there is no second ledger. The [SQL proposal](proposals/0005-byok.sql) extends attempts for multiple calls and immutable terms. It is **outside the migration runner**, pending Task 01 review after identity 0004. A required `CallDispatchGate.lockAndAuthorize(tx,terms)` handles E1 global/project/job/step locks, lease/state/owner/cancellation/cleanup/kill-switch checks, exact admitted policy/price and credential revision. There is no permissive production implementation. Native tests use a clearly labeled fixture gate.

A scoped receipt authenticates settlement to the trusted worker role. Measured bounded tokens settle once at the pinned version; settlement digest includes the full payload so conflicting repeats fail. Missing/estimated/out-of-bound usage, transport failures, timeout and cancellation retain the maximum. Cache-discounted or unknown cache/tier usage remains uncertain because Provider v1 cannot represent those price components; it requires authenticated provider invoice evidence and Task 01's reviewed adjustment/reconciliation path. It is never booked at zero or silently overcharged at an uncached estimate. Late authenticated usage can settle an expired lease; it does not grant dispatch or source adoption authority.

Before live composition, Task 01 must include **reserved** as well as dispatched/uncertain attempts in cleanup liability; wire settlement/release to the global envelope, immutable policy admission, safe events and audited invoice adjustments; and define consistent lock order across cancellation, credential rotation and settlement. Reserved intents from a crash require explicit reconciliation, not automatic replay. No partial SQL application enables generation.

`generatePlan` and `generateAccountedSource` consume these hooks. The source stage collects semantically bound batches, builds immutable source and raw hashes, creates the exact diff and calls a separately fenced `adopt` callback. Each repair produces a new execution review. Only Task 01 can widen the fixture-only stage/result composition after validation; Task 04 never relabels fixture runner/build/cleanup outcomes. No generated code executes here.
